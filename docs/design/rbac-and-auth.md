# Authentication

KeenySpace authentication follows a similar model to Anthropic's API: OIDC for interactive
human users, and long-lived API keys for programmatic and agent access.

Authorization (roles, ACL, group mappings beyond the entry gate and the admin group) is
deferred to v1.5. v1 is single-org: all authenticated users see all workspaces.

## Authentication surfaces

### OIDC (interactive users)

Login flow:
1. User runs `keenyspace login` — opens a browser tab via the device-code flow.
2. Browser is directed to the OIDC IdP (Authentik in the reference setup).
3. IdP authenticates the user and returns an authorization code.
4. Server exchanges the code for tokens, validates the JWT, creates a session.
5. CLI receives a session token and stores it in `~/.config/keenyspace/auth.json` (mode 0600).

OIDC discovery is available at `GET /v1/api/auth/discovery`. Any standards-compliant OIDC
provider works at the protocol level; Authentik is the reference for v1.

### API keys (agents and programmatic access)

Format: `ks_live_<random>` (32 random bytes, URL-safe base64). Generated by the server,
shown plaintext once on creation.

Usage: `Authorization: Bearer ks_live_...` in HTTP and MCP requests.

API keys are the **primary auth path for MCP agents**. OIDC bearer tokens are short-lived
(hours), which is incompatible with long-running MCP sessions. Any authenticated user can
mint keys for themselves via `POST /v1/api/auth/api-keys`. Keys do not expire by default;
`expires_in_days` (1-3650) at mint time sets `expires_at`, after which the key is
refused. Mint and revoke are written to the audit log in the same transaction as the key
change.

API keys are stored as argon2id hashes. Lookup uses a sha256+pepper hash for fast index
lookup before argon2 verification. Successful verifications are cached in-process for 60
seconds; revocation, revoke-all, a change of the owner's group snapshot and a restore
drop the cached entries.

A key authenticates as its owner with the owner's **group snapshot**: the groups from the
owner's most recent OIDC token that carried a `groups` claim, stored in `users.groups` /
`users.groups_seen_at` and refreshed on every such OIDC request
(`auth/group_snapshot.py`). A key whose owner has no snapshot carries no groups.
`KEENYSPACE_AUTH__API_KEY_GROUP_SNAPSHOT_MAX_AGE_DAYS` (unset by default) refuses keys
whose snapshot is older than that many days.

### MCP authentication

MCP requests go through the same `CompositeAuthBackend` middleware as HTTP requests. The
single `Starlette AuthMiddleware` at the FastAPI root covers both transports. FastMCP tools
read the caller identity via `auth_bridge` from `get_http_request().state.user`. FastMCP's
built-in OAuthProxy is not used (incompatible with the mount-path architecture).

## Group entry gate (D-05)

Membership in a specific IdP group can be required for access. When
`KEENYSPACE_AUTH__REQUIRED_GROUP` is set (the compose file defaults it to
`keenyspace-users`; the server default is empty, meaning no gate),
`CompositeAuthBackend.authenticate()` checks the principal's groups after validation:
the `groups` claim for OIDC tokens, the owner's group snapshot for API keys. Requests
from users not in the required group receive HTTP 401.

Because API keys are checked against a snapshot, removing a user from the group in the
IdP reaches their keys only on their next OIDC request, or when the snapshot max age
expires. Offboarding therefore also revokes the user's keys via
`POST /v1/admin/api-keys/revoke-all`.

## Admin group

The admin API (`/v1/admin/backup`, `/v1/admin/restore`, `/v1/admin/api-keys/revoke-all`)
is mounted only when `KEENYSPACE_ADMIN_API_ENABLED=1`. Each route additionally requires
membership in `auth.admin_group` (`KEENYSPACE_AUTH__ADMIN_GROUP`, default
`keenyspace-admins`), checked in `AdminRoute` (`auth/admin_gate.py`) with the same group
sources as the entry gate. Non-members receive HTTP 403. The check runs before the
request body is parsed, so a non-admin restore upload is refused before it is spooled to
disk. An empty environment value falls back to the default.

## Trust model

- **Server admin is trusted.** SSH access to the server filesystem bypasses all auth. This
  is standard practice for self-hosted software (Postgres, Outline, GitLab).
- **Server trusts JWTs signed by the configured IdP.** JWKS are fetched from the IdP and
  cached with periodic refresh. Only access tokens are accepted as bearer credentials:
  a JWT without a `scope` claim (an ID token) is refused.
- **TLS is terminated externally** by the reverse proxy (Caddy or nginx). The server
  speaks plain HTTP internally.

## Auth middleware

Single `Starlette AuthMiddleware` on the FastAPI root app. It is installed before the MCP
mount (`app.mount("/v1/mcp", ...)`) so that all requests to both `/v1/api/*` and `/v1/mcp`
are covered by the same check. The middleware runs before route handlers and populates
`request.state.user` with the resolved `User` or raises `AuthenticationError`.

`/healthz` and `/readyz` are exempted from auth requirements. `/metrics` is not public:
Prometheus metrics are served on a separate internal listener (`KEENYSPACE_METRICS_PORT`,
default 9100), and a request to `/metrics` on the API port goes through the auth
middleware like any other path.
